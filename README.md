# frontend-workflow-lab

> **English summary.** A small React + TypeScript app for one question: how do you keep a multi-step
> workflow (draft → issue → seen → reply) correct on the client? State is one plain object changed only by
> pure transitions that return `{ ok, state }` or `{ ok: false, state, reason }`, so the screen can say why
> something cannot be done. Permissions and visibility are decided in the domain layer, not by hiding
> buttons. A notice keeps a copy of what was issued. Screens subscribe with selectors. A saved state is
> fully validated before use, and an older shape is lifted without inventing data it never had.
> It runs in one browser with a role switcher; there is no server and no real delivery between people.
> 65 unit tests and a 24-step check in a real headless Chrome.

한 사람이 통보를 발행하고 다른 사람이 열람하고 회신하는 흐름을, 화면 쪽에서 어떻게 틀리지 않게 만들 것인가를 다룬 작은 예제입니다.

팀 프로젝트의 화면 시안에서 쓴 설계 원칙을 그 프로젝트의 코드 없이 혼자 볼 수 있는 크기로 다시 만든 것입니다. 제품의 소스가 아니며 코드를 공유하지 않습니다.

**범위.** 서버가 없습니다. 한 브라우저에서 "보는 사람"을 바꿔 가며 확인하는 예제이고, 사람 사이의 실제 전송과 동기화는 다루지 않습니다. 보는 사람을 바꾸는 것은 로그인이 아니며, 여기서 말하는 "보이지 않는다"는 화면이 그리지 않는다는 뜻입니다. 실제 제품에서는 서버가 권한을 검사해야 합니다.

## 실행

```
npm install
npm run dev      # 화면
npm test         # 단위 시험 65개
npm run build    # 형 검사 + 빌드
npm run e2e      # 실제 Chrome으로 24단계 검사 (빌드 뒤에)
```

## 규칙

| 무엇 | 규칙 |
|---|---|
| 보이는 범위 | 점검 담당은 전부. 참관은 초안을 뺀 전부. 업체 담당은 자기 업체의 지적과 발행된 통보만 |
| 열람 | 사람마다 기록합니다. 동료가 회신한 뒤에도 내가 열지 않았으면 나에게는 읽지 않은 통보입니다 |
| 회신 | 업체마다 한 번입니다. 회신한 사람은 읽은 것이므로 열람이 먼저 기록됩니다. "회신 → 열람" 순서의 이력은 한 사람에게 생기지 않습니다 |
| 발행본 | 발행하는 순간의 지적 내용을 복사해 둡니다. 뒤에 지적을 고쳐도 통보는 그대로입니다 |

## 설계

### 1. 상태는 객체 하나, 바꾸는 것은 순수 함수뿐 (`src/domain/actions.ts`)

상태를 바꾸는 함수는 `(상태, 인자) → 결과`이고 받은 상태를 고치지 않습니다. 시험은 상태를 깊게 얼린 채 돌리므로, 제자리에서 고치는 코드가 있으면 통과하지 못합니다.

### 2. 거절은 까닭과 함께 돌려준다

거절할 때 받은 상태를 그대로 돌려주기만 하면 화면은 "아무 일도 일어나지 않았다"만 압니다. 권한이 없어서인지, 내용이 비어서인지, 이미 발행돼서인지 구분하지 못합니다.

```ts
type Result =
  | { ok: true; state: AppState }
  | { ok: false; state: AppState; reason: Refusal };
```

### 3. 화면은 규칙을 따로 갖지 않고 상태 함수에 묻는다 (`src/domain/selectors.ts`)

상태 함수가 순수 함수이므로 화면은 "지금 이 사람이 이것을 누르면 어떻게 되는가"를 그 함수에 그대로 물어볼 수 있습니다. 결과에 따라 단추를 셋으로 나눕니다.

- 이 사람은 영영 할 수 없는 일 (권한 없음 · 다른 업체) → 단추를 그리지 않습니다.
- 지금 상태에서만 안 되는 일 (이미 발행됨 · 내용이 빔) → 단추를 끄고 까닭을 옆에 적습니다.
- 할 수 있는 일 → 켭니다.

화면용 규칙을 따로 적지 않으므로 화면과 상태 함수가 서로 어긋날 수 없습니다. 그래도 거절되는 요청(낡은 화면, 직접 호출)은 까닭이 알림으로 나옵니다.

### 4. 무엇이 누구에게 보이는지는 한 곳에서 정한다

화면은 `state.findings`나 `state.notices`를 직접 읽지 않고 `visibleFindings` · `visibleNotices` · `visibleStatusCounts`에 묻습니다. 건수도 그 사람에게 보이는 것만 셉니다.

### 5. 계산할 수 있는 값은 저장하지 않는다

상태별 건수, 읽지 않은 통보 수, 누구에게 무엇이 보이는지는 저장하지 않고 상태에서 계산합니다.

### 6. 화면은 필요한 값만 구독한다 (`src/store/store.ts`)

컨텍스트 하나에 상태 전체를 넣으면 값 하나가 바뀔 때 그것을 읽는 화면이 모두 다시 그려집니다. 여기서는 `useSyncExternalStore`와 선택 함수로 구독합니다. `tests/render.test.tsx`가 횟수를 셉니다.

| 상태를 10번 바꿈 (보여 주는 값과 무관한 변경) | 다시 그린 횟수 |
|---|---|
| 상태 전체를 읽는 컴포넌트 | 10 |
| 값 하나를 고른 컴포넌트 | 0 |

목록을 돌려주는 선택 함수는 입력이 같은 객체인 동안 같은 배열을 돌려주도록 마지막 결과를 기억합니다.

### 7. 저장본은 전부 검사한 뒤에 쓴다 (`src/domain/migrate.ts`)

브라우저에서 꺼낸 저장본은 화면이 읽기 전에 한 문을 지나야 합니다. 자료형, 허용된 값, 발행본 안의 지적 목록, 상태와 발행본과 회신이 서로 맞는지, 번호가 서로 가리키는 대상이 있는지를 모두 봅니다. 하나라도 어긋나면 반쯤 읽지 않고 까닭과 함께 거절한 뒤 처음 상태로 열고, 화면에 그 사실을 알립니다.

1판 저장본은 2판 모양으로 올려서 엽니다. 1판은 "열람했는가"를 참·거짓 하나로만 저장했으므로, 올린 기록은 "열람됨 · 열람자와 시각 미상"입니다. 누가 봤는지와 언제 봤는지는 지어내지 않습니다.

브라우저 저장소가 막혀 있으면 읽기에서도 예외가 납니다. `window.localStorage`에 손을 대는 것만으로 예외가 나는 경우까지 포함해, 그럴 때는 메모리에서 동작합니다.

## 검사

| 종류 | 수 | 확인하는 것 |
|---|---|---|
| `tests/actions.test.ts` | 31 | 흐름 · 거절 까닭 · 잘못된 입력 · 역할별 권한 20가지 · 발행본 보존 · 파생 값 |
| `tests/migrate.test.ts` | 10 | 1판 저장본 올리기 · 깨진 저장본 거절 · 새로고침 뒤 상태 유지 |
| `tests/ui.test.tsx` | 5 | 화면을 눌러 끝까지 가는 흐름 · 누르기 전에 까닭 표시 · 사람마다 다른 단추 |
| `tests/render.test.tsx` | 2 | 다시 그리는 횟수 |
| `tests/audit.test.tsx` | 17 | 아래 "검토에서 찾은 결함"의 회귀 시험 |
| `e2e/run.mjs` | 24 | 실제 Chrome에서 세 사람의 흐름 · 새로고침 · 390px 폭에서 가로 넘침과 삐져나온 칸 없음 · 깨진 저장본 · 막힌 저장소 · 페이지 오류 0 |

브라우저 검사는 의존성을 더하지 않고, 설치된 Chrome을 띄워 개발자 도구 프로토콜로 직접 구동합니다.

권한 시험 20가지는 이 예제의 다섯 동작을 등록된 네 사람으로 부른 것입니다. 권한 모델 전체가 빈틈없다는 증명은 아닙니다.

시험이 실제로 잡아내는지는 코드를 일부러 망가뜨려 확인했습니다.

- 발행 함수에서 역할 검사를 빼면 시험이 실패합니다.
- 통보가 발행본 대신 지금 원본을 보이게 바꾸면 시험이 실패합니다.

## 검토에서 찾은 결함

첫 판은 시험 46개가 모두 통과했습니다. 그런데 바깥에서 코드를 검토받자 그 46개가 놓친 결함이 나왔습니다. 결함마다 실패하는 시험을 먼저 쓰고(14개가 실패하는 것을 확인) 고쳤습니다.

| 결함 | 원인 | 고친 방법 |
|---|---|---|
| 다른 업체 담당에게 남의 업체 지적 내용과 전체 건수가 보임 | 통보만 걸렀고 지적 목록과 건수는 상태에서 직접 읽음 | 보이는 범위를 정하는 함수를 한 곳에 모으고 화면이 그것만 쓰게 함 |
| 발행본의 지적 목록이 빠진 저장본을 정상으로 읽고 나중에 화면이 죽음 | 저장본 검사가 겉의 몇 칸만 봄 | 저장본 전체를 검사하는 한 문을 만들고 올린 저장본도 같은 문을 지나게 함 |
| 옛 저장본을 올리면서 그 업체의 첫 담당자를 열람자로, 발행 시각을 열람 시각으로 적음 | 모르는 값을 그럴듯한 값으로 채움 | 열람자와 시각을 "미상"으로 기록하고 화면에 그대로 표시 |
| 저장소 읽기가 예외를 던지면 앱이 뜨지 않음 | 쓰기 실패만 처리함 | 읽기 실패도 처리하고 메모리에서 시작 |
| 한 사람의 이력이 "발행 → 회신 → 열람"이 됨 | 열람과 회신의 관계를 정하지 않음 | 회신이 열람을 먼저 기록하게 함 |
| 동료가 회신하면 아직 열지 않은 사람의 읽지 않은 통보가 0이 됨 | 읽지 않음을 통보의 상태로 계산함 | 사람마다의 열람 기록으로 계산함 |

고친 뒤 실제 Chrome으로 검사하다가 하나를 더 찾았습니다. 저장소가 막힌 브라우저에서는 `getItem`을 부르기 전에 `window.localStorage`에 손을 대는 순간 예외가 나는데, 단위 시험은 `getItem`이 던지는 경우만 흉내 냈습니다. 저장소에 손을 대는 일을 호출 안으로 옮기고 그 경우를 시험에 넣었습니다. 또 휴대폰 폭에서 입력 칸이 본문 단보다 오른쪽으로 삐져나오는 것을 화면 캡처에서 보고, 그것을 재는 검사를 먼저 실패시킨 뒤 고쳤습니다.

이 일에서 얻은 것은 "시험이 통과한다"와 "규칙이 옳다"가 다른 말이라는 것입니다. 첫 판의 시험은 제가 생각한 경우만 확인했습니다.

## 한계

- 서버가 없어 여러 사람이 동시에 고치는 경우, 전송 실패, 순서 뒤바뀜을 다루지 않습니다.
- 화면은 흐름을 확인하려는 실습 화면입니다. 디자인과 접근성은 제품 수준으로 다듬지 않았습니다. 브라우저 검사가 보는 접근성은 이름으로 요소를 찾을 수 있는가 정도입니다.
- 끈 단추 옆의 까닭 가운데 "지금 상태에서는 할 수 없는 일입니다"는 뭉뚱그린 문장입니다. 이미 발행됐는지 이미 회신됐는지를 나눠 말하지 않습니다.
- 저장본을 올리는 코드는 1판 → 2판 한 단계뿐입니다.
